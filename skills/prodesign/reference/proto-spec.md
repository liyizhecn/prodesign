# prodesign 原型输出规范

> 路径约定：下文 `$SKILLS` 指本套件的安装根目录——项目级 `.claude/skills`（优先）或全局 `~/.claude/skills`，按实际存在解析。


原型阶段（/prodesign-proto）的强制规范。目标：原型是可交互、可机械验证、数据自洽的"演示世界"，不是静态示意图。
配套强制规范：**`patterns.md`（五种页型的标准结构与页型声明）**、**`content-spec.md`（数据格式与文案词表）**——建页前同读。

## 1. 技术约束

- **零外部依赖单文件 HTML（硬约束）**：CSS/JS 全部内联，禁止任何 `http(s)://` 的 src/href/字体/CDN 引用（validate 会拦截）。这是刻意的**交付特性**，不是技术保守：双击即开（评审投屏/邮件分发/客户现场）、归档不腐坏（原型是 PRD 的冻结附件证据）、jsdom 直接可测。原型定位是**设计交付物**，不是代码基线——不要为"代码复用"引入构建链。
- 设计语言、主色（种子层 token）、目标分辨率在 project.md「原型全局约束」中实例化；同一产品所有原型页保持一致。
- 文件命名：`<模块中文名>_原型.html`，与已交付原型风格一致。

## 2. 设计令牌（token）纪律

样式一致性不靠自觉，靠 token + 机械校验。三层结构（借鉴 Ant Design v5 模型）：

| 层 | 前缀示例 | 职责 |
|---|---|---|
| 种子 seed | `--seed-primary` | 真正的设计输入，只有几个；换主题只动这层 |
| 派生 map | `--primary-hover` `--text-2` `--border` | 从种子推导的梯度、中性色、阴影 |
| 语义 alias | `--menu-selected-bg` `--table-row-selected` `--tag-high-*` | 按**用途**命名；组件样式只消费这层与 map 通用项 |

硬规则（validate 机械拦截）：

1. **一切色值（hex / rgb / hsl / 渐变）只允许出现在 `:root` 令牌层**；组件样式与行内 style 一律引用 `var(--*)`。
2. **页面不得私自增删改 token**：需要新 token 或新组件样式 → 先加进骨架基座，再回页面使用（校验器断言每页 `:root` 与骨架逐条一致）。
3. 图表/热力图等需要色阶时，色阶也进令牌层（`--chart-1..n`）。

## 3. 骨架基座（页面唯一起点）

- **首版原型交付时实例化**：从 `$SKILLS/prodesign/templates/page-skeleton.html` 复制为 `deliverables/tools/_页面骨架.html`，改产品名、菜单项、种子层色值，按产品需要增删组件样式。骨架同时是设计规范的**活文档**（自带全组件样例区）——单文件版的 Storybook。
- **新建原型页 = 复制骨架 → 删样例区 → 写页面内容**。不要抄相邻页（相邻页可能带着旧版骨架或页面私货）。
- 骨架的结构类名（`.app` / `.sidebar` / `.topbar` / `.content`）是校验器断言对象，不许改名。
- **骨架演进策略**：骨架属"活工具"可直接维护（变更记 changelog），但**已交付页面冻结不回刷**——新页用新骨架，历史页差异按"渐进铺设"记入已知边界（与编号让路原则同一思想）。
- **侧边栏菜单唯一事实源**：`deliverables/tools/_菜单模板.html`，与骨架同批建立；每页菜单必须与模板一致（渐进铺设的差异写进校验器白名单）。
- 每页含**页面状态切换器**（数据态 / 加载态 / 空态）；**深链协议** `?focus=<实体ID>` 定位并高亮目标行（骨架已内置两者的参考实现）。

## 3.1 演进路径（预留，当前不启用）

- **构建注入（升级选项）**：若骨架复制漂移的修复成本随页面数增长到难以接受，可升级为"源页面 + `<!-- @base -->` 标记，archive 时由脚本注入骨架装配单文件交付物"——交付物仍是单文件，骨架变为单一事实源。触发条件：校验器频繁报漂移且修复成为负担。
- **开发交接（建议动作）**：进入开发时，把骨架 `:root` 令牌层导出为 token 对照表交给前端，在真实技术栈（如 React+Tailwind）里复刻同名 CSS 变量——原型与产品代码各活各的，token 是桥。

## 4. 种子数据

- 演示实体（部门/人员/模型/ID/金额）一律取自 project.md 事实源清单或已交付原型；新实体先登记再使用。
- 数据自洽三条：① 汇总恒等（各分项之和 = 总计）；② ID 格式与 PRD 附录的 ID 规范一致；③ 跨页时序咬合（页面 A 展示的配置变更，在审计/日志类页面 B 有对应记录且时间先后合法）。
- 演示态要覆盖 PRD 5.2/5.3 定义的关键状态与边界条件，每种至少一个演示位。

## 5. 断言规范（checks/*.js）

- 用 jsdom 真实运行原型（`runScripts:'dangerously'`），从 `checks/_template.js` 起步。需要 `jsdom` 依赖：在有 node_modules 的目录运行，或 `npm i --no-save jsdom`。**注意 jsdom 无 scrollIntoView 等 API，先打桩**；不要用 try/catch 盲扫掩盖调用错误。
- **每条断言锚定编号**：`chk('F18-08', '静默窗口首条实发', cond)` —— 第一个参数必须是 PRD 里的 F/A 编号或「原型说明」。
- 三类高价值断言，尽量都有：
  1. **结构性恒等式**：两处独立展示的同一事实必须相等（铃铛未读数 ≡ 收件箱未读条数；cost ≡ units × 单价）。
  2. **反向结构验证**：不该存在的能力断言其不存在（审计不可删改 → 页面不存在任何删改函数；零明文 → documentElement 级搜索无密码痕迹）。
  3. **布局断言**：computed-style 级检查关键容器（功能测试全绿不等于页面能看；断言基座类名、顶栏位置等）。
- 断言用**元素级选择器**，不要跨行正则串匹配整页文本（脆弱且多次踩坑）。
- 空数组陷阱：`[].every(...)===true`——涉及"全部满足"的守卫先断言集合非空。

## 6. 产品自有校验器（validators）

校验分两层：skill 的 `prodesign.mjs` 只做产品无关的机械检查；**产品相关的校验知识（菜单结构、跨页数据自洽规则）放在产品资料库里**，即 `deliverables/tools/validators/*.js`——validate 运行时会自动逐个执行（约定：`node <校验器> <工作区prototypes目录> <deliverables/prototypes目录>`，非零退出=校验失败）。

- **首版原型交付时**，与 `_菜单模板.html` 一起，从 `$SKILLS/prodesign/templates/validator-template.js` 生成产品校验器（模板内置五查：**菜单签名 / token 漂移 / 基座类名 / 页型必备元素（meta page-type）/ token 对比度（WCAG AA 自动计算）**，按产品真实 DOM 调整选择器后启用）——生成它的会话知道本产品的真实 DOM 结构，选择器按实际结构写死，这就是适配的来源。
- 后续版本**只维护不重写**：菜单新增项时先改 `_菜单模板.html`，validators 负责抓所有页面的漂移（渐进铺设允许的差异写进校验器的白名单并注释理由）。
- validators 与菜单模板属于"活工具"，允许直接在 deliverables/tools/ 维护（不受冻结原则约束），但每次变更记入当版 changelog。
- 校验器保持零依赖（正则/字符串抽签名），不引 jsdom——它要在任何环境跑得动。

## 7. 交付自检

- 跑通全部 checks，输出「通过 N / N」；失败项修复原型或（确属规格问题时）回改 PRD 并记录到 review.md。
- 修代码不改断言：断言失败优先怀疑实现；确需改断言时在 changelog 中说明理由。
- 写「已知边界」：未铺设页、演示模拟项（真实定时器/加解密/后端行为）、未做的交互，逐条列出。
